# การใช้ AI ในการพัฒนา

เอกสารนี้อธิบายว่าโปรเจกต์ **ระบบจัดการการบำรุงเครื่องจักร** ใช้ AI ในการพัฒนาอย่างไร
AI ช่วยงานอะไรบ้าง และอะไรที่ต้องให้มนุษย์ตรวจเอง

---

## เครื่องมือที่ใช้

| รายการ | รายละเอียด |
| --- | --- |
| **AI coding assistant** | OpenCode (ใช้โมเดล Claude โดยผ่าน opencode/big-pickle) |
| **บทบาทของมนุษย์** | ผู้วางแผน ตัดสินใจ และตรวจสอบผลลัพธ์ทุกขั้นตอน |
| **รูปแบบการทำงาน** | สั่งงานเป็นส่วน ๆ → ตรวจผล → สั่งแก้ → ตรวจซ้ำ |

> ส่วนนี้เขียนขึ้นเพื่อความโปร่งใส ไม่ได้ทำให้โปรเจกต์ดูดีเกินจริง
> ทุกข้อด้านล่างเป็นสิ่งที่เกิดขึ้นจริงระหว่างพัฒนา

---

## 1. สิ่งที่ AI ช่วยได้

### 1.1 ออกแบบฐานข้อมูล

AI เขียน migration ทั้ง 2 ไฟล์ คือ
[`supabase/migrations/001_init.sql`](../supabase/migrations/001_init.sql) และ
[`002_user_approval.sql`](../supabase/migrations/002_user_approval.sql) รวมถึง

- 5 enum (`app_role`, `machine_status`, `alarm_status`, `maintenance_status`, `maintenance_priority`)
- 4 ตาราง (`profiles`, `machines`, `alarms`, `maintenance_records`)
  พร้อม CHECK constraint ป้องกันค่าว่าง ค่าติดลบ และบังคับเวลาให้สอดคล้องกับสถานะ
- 14 ดัชนี ครอบคลุมการค้นหาที่ใช้จริง เช่น `alarms_occurred_idx` และ `profiles_pending_idx`
- RLS policy ทุกตาราง
- 7 ฟังก์ชัน ได้แก่ `handle_new_user()`, `set_updated_at()`, `current_role()`,
  `is_admin()`, `is_approved()`, `can_access_system()`, `protect_profile_approval()`
- 2 view สำหรับ Dashboard (`machine_status_counts`, `alarm_status_counts`)

### 1.2 ระบบอนุมัติผู้ใช้

ช่วยออกแบบ flow `สมัคร → รออนุมัติ → เข้าใช้งาน` และเขียนโค้ดส่วนนี้ครบทั้งหมด

- Server Actions ใน `app/actions/auth.ts` และ `app/actions/users.ts`
- หน้า `/signup`, `/pending` และ `/users`
- `requireApprovedUser()` / `requireAdmin()` ใน `lib/data/auth.ts`
- การ redirect ผู้ยังไม่อนุมัติไป `/pending` ทั้งตอน login และเข้าเว็บ

### 1.3 ชั้นความปลอดภัย 3 ชั้น

AI ช่วยคิดว่าการซ่อนปุ่มใน UI ไม่ใช่การป้องกันสิทธิ์ จึงต้องบังคับพร้อมกัน 3 ที่

1. **RLS policy** — บังคับที่ระดับฐานข้อมูล (ชั้นที่สำคัญที่สุด)
2. **DAL** — `lib/data/auth.ts` ตรวจก่อน query
3. **Server Actions** — ตรวจซ้ำก่อนเขียนข้อมูลทุกครั้ง

รวมถึง trigger ที่กันไม่ให้ผู้ใช้อนุมัติหรือยกเลิกสิทธิ์ของตัวเอง

### 1.4 CRUD ทั้งระบบ

เครื่องจักร, Alarm และงานบำรุง ทั้งฝั่ง Server Actions, DAL, ฟอร์ม และตารางแสดงผล
รวมถึง validation ด้วย Zod ใน `lib/validation.ts`

### 1.5 ระบบค้นหาข้ามตาราง

แก้ปัญหาค้นหา Alarm และงานบำรุงด้วยชื่อเครื่องจักร โดยให้ใช้

- `findMachineIdsBySearch()` ใน `lib/data/machines.ts` เพื่อหา id ของเครื่องที่ตรงกับคำค้นก่อน
- `escapeLikePattern()` ใน `lib/utils/search.ts` เพื่อกัน SQL injection และไม่ให้ `%` ในคำค้น
  กลายเป็น wildcard

### 1.6 Dark mode

AI เสนอวิธี override ตัวแปรสีของ Tailwind ทั้งชุดในคลาส `.dark` แทนการเขียน `dark:`
ราว 190 จุดทั่วทั้งโปรเจกต์ และช่วยแก้สีกราฟที่เดิมเขียนเป็น hex ตรง ๆ ให้เป็น
`var(--color-*)` เพื่อให้เปลี่ยนตามธีม — ปัจจุบันตรวจแล้วไม่มี hex 6 หลักเหลือใน
`app/`, `components/` และ `lib/` แล้ว

ผลลัพธ์ใน `app/globals.css` คือ override สี 35 ตัว ใน 6 ตระกูล
(`slate`, `red`, `emerald`, `amber`, `blue`, `zinc`) ภายใต้ `.dark` เดียว

### 1.7 สคริปต์ทดสอบ

| สคริปต์ | ผล | ใช้ทำอะไร |
| --- | --- | --- |
| `scripts/verify-approval.mjs` | ผ่าน 10/10 | ทดสอบวงจรอนุมัติผู้ใช้ผ่าน REST API แล้วลบข้อมูลทดสอบเอง |
| `scripts/check-dark-contrast.mjs` | ผ่าน 36/36 | แปลง oklch → sRGB แล้วคำนวณคอนทราสต์ตาม WCAG AA |

### 1.8 GitHub Actions และเอกสาร

- เขียน `.github/workflows/ci.yml` ตามลำดับ Install → Build → Lint → Test
- ตรวจพบว่า `actions/checkout@v4` ใช้ Node 20 ที่ GitHub เลิกรองรับ แล้วแก้เป็น v5
- เขียนและปรับ README รวมถึงคู่มือติดตั้ง

## 2. จุดที่ AI ทำผิด และมนุษย์ต้องตรวจเอง

หัวข้อนี้สำคัญที่สุด เพราะเป็นข้อยกเว้นว่า AI **ไม่ได้ถูกต้องเสมอ**
ทุกข้อด้านล่างเป็นบั๊กจริงที่เจอระหว่างพัฒนา

### 2.1 คอนทราสต์ของสี (dark mode)

**สิ่งที่ผิด:** AI เดาค่าสี oklch โดยไม่ได้คำนวณ ผลคือค่าที่ได้ไม่ตรงเป้าที่ตั้งใจ
และ audit โค้ดด้วย regex พบว่า **ลืม override ชั้น `-800` ของ `red`, `emerald`, `blue` และ `amber`**
(ปัจจุบัน override ครบทั้ง 5 ตระกูลแล้ว) ทำให้ป้ายสถานะมีตัวอักษรเข้มอยู่บนพื้นเข้ม มองไม่ออกเลย

**วิธีตรวจ:** เขียน `scripts/check-dark-contrast.mjs` อ่านค่าจริงจาก `app/globals.css`
แปลง oklch → sRGB แล้วคำนวณอัตราส่วนคอนทราสต์ตามมาตรฐาน WCAG แทนการดูด้วยตา
รวมถึง audit คลาสสีทั้งหมดในโค้ดด้วย regex เพื่อหาว่าใช้ระดับสีอะไรบ้างจริง ๆ

**ผลลัพธ์:** สคริปต์รายงานคู่ที่ไม่ผ่านจนกว่าจะแก้ครบ ปัจจุบันรันแล้วผ่านครบ 36 คู่
และเพิ่มเข้า CI เป็นขั้นตอน Test เพื่อกันไม่ให้บั๊กนี้กลับมา

### 2.2 React Hooks / hydration

**สิ่งที่ผิด:** ปุ่มสลับธีมเวอร์ชันแรกใช้ `useState` + `useEffect` เพื่ออ่านธีม ซึ่ง ESLint
(React Compiler rules) ไม่อนุญาต และเสี่ยง hydration mismatch

**วิธีตรวจ:** รัน `npm run lint` และ `tsc --noEmit` หลังเขียนเสร็จทุกครั้ง ไม่ใช่รอ build

**วิธีแก้:** ตัด state ออกทั้งหมด ใช้ CSS `dark:` variant ตัดสินใจว่าจะแสดงไอคอนใด
ซึ่งไม่มี state เลยจึงไม่มีปัญหา hydration โดยต้องประกาศ `@custom-variant dark` เพิ่ม

### 2.3 Lock file ไม่ sync

**สิ่งที่ผิด:** `npm ci` ล้มเพราะ `package-lock.json` ไม่ตรงกับ `package.json`
(optional dependency `@emnapi/*` เก่า) ซึ่งจะทำให้ CI ล้มตั้งแต่ขั้นตอนแรก

**วิธีตรวจ:** รัน `npm ci` จริง ไม่ใช่เชื่อว่าไฟล์ lock ถูกต้อง (เคยรัน `npm install` แล้วเชื่อว่าเพียงพอ)

### 2.4 ความปลอดภัยของ secret

**สิ่งที่ผิด:** ไม่ควรไว้ใจว่า `.gitignore` อย่างเดียวพอ

**วิธีตรวจ:** อ่านค่าจริงจาก `.env.local` แล้วค้นหาค่านั้นในทุกไฟล์ที่ git จะนำขึ้น
(ทั้งระหว่างทำ และซ้ำอีกครั้งกับ staged content ก่อน commit) โดยไม่พิมพ์ค่าลับออกมา
ผลคือพบเฉพาะ `NEXT_PUBLIC_SITE_URL` ซึ่งเป็น public var ไม่ใช่ความลับ

### 2.5 การอ่านเอกสารของเฟรมเวิร์ก

Next.js 16 มีการเปลี่ยนแปลง (เช่น `proxy.ts` แทน `middleware.ts`) จึงต้องอ่าน
`node_modules/next/dist/docs/` ก่อนเขียนโค้ด แทนการใช้ความจำจากเวอร์ชันเก่า

## 3. สิ่งที่ไม่ได้ให้ AI ทำ

- **ไม่ได้รัน migration บนฐานข้อมูลจริงโดยไม่ตรวจ** — ทุก constraint ตรวจทีละตัวก่อนรัน
  และตรวจผลด้วย service role ว่าตารางถูกสร้างจริง
- **ผลทดสอบในเบราว์เซอร์ต้องทำด้วยมือ** — สลับธีม ดูความคมชัด กดปุ่มต่าง ๆ AI ทำแทนไม่ได้
- **การตั้งค่า GitHub Actions / billing** — ต้องทำผ่านหน้าเว็บของ GitHub
- **การ deploy ขึ้น Vercel และตั้ง secret ใน production** — ต้องทำเอง
- **การตัดสินใจว่าจะอนุมัติผู้ใช้รายใดรายหนึ่ง** — เป็นการตัดสินใจของมนุษย์เท่านั้น

---

## 4. สรุป

AI ช่วยได้มากในงานที่ซ้ำซ้อนและมีรูปแบบชัดเจน เช่น เขียน migration, เขียน CRUD,
เขียนเอกสาร แต่งานที่ผลลัพธ์ "ถูกหรือผิด" ตัดสินได้ด้วยการรันคำสั่ง เช่น คอนทราสต์ของสี,
ความถูกต้องของ lock file, ความปลอดภัยของ secret ต้องให้มนุษย์สั่งการตรวจเสมอ

หลักการที่ใช้ตลอด: **ให้ AI ลงมือทำ แต่ให้มนุษย์ตรวจด้วยเครื่องมือที่วัดผลได้**
ไม่เชื่อคำบอกเล่าว่า "น่าจะถูก" แต่ต้องมีคำสั่งที่รันแล้วผ่าน
